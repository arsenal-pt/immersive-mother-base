# Services, animation and actor capabilities

## A service requires a real supported endpoint

Model needs and services as explicit state. A need can only be relieved after the actor arrives at a currently available service and completes its supported action. A proposed room, idle pose, queue marker or UI button is not a service. If a route, actor family, animation or fixture interaction is unbound, fail closed and show the missing capability.

The private Command2 service pilot used one-node standing routes selected from the normal Mother Base FRT, with completed-grade, mission, cluster, layout and route-hash gates. The authored binding had no coordinates or engine calls; it consumed a validated catalog. Route positions were already mission-world coordinates and were not transformed again. A numeric route-name argument still required native acceptance. Generated water/mess/rest pads were candidates, not proof of drinking, eating, sleeping or working. Shower, toilet and clinic remained unbound there.

The native test should route one observed actor, confirm the same actor remains enabled and normal, measure actual position through strict arrival and dwell thresholds, then restore the previous route. Test queue → arrival → use → timed completion → roam, plus cancellation by muster, danger, unavailability and departure. No reward before observed completion. A short test or route acceptance cannot unlock a different endpoint.

## Capability matrix by actor family

Maintain capabilities per actor family and action: identity/read, route assignment, stable hold, native status, service, conversation, CQC, animation, original-controller return. A single pass must not imply the whole row passes. Hostage2 IH actors in later inspection did not inherit Soldier2 CQC/services simply because a logical record was adopted. Children and named story controllers stay protected unless a specific bounded capability proof says otherwise.

One failed IH 0.2.5 mixed-group preflight found addressing ambiguity before any movement attempt. This is not a walking failure. Later ownership remained off with no physical proofs. Do not reinstall the same failed candidate and call the result new evidence.

## Animation facts and unknowns

Use exact observed actor state and animation events where available. The recorder's native 0.1.2 sample captured 25 position/time samples over about five seconds, matched the player position against the bridge, and recorded one mark and zero events. Exact animation IDs were unavailable. It did not verify demonstration events, full duration/endurance or exact NPC replay. A recorder being installed and sampling position is not animation discovery. Earlier recorder 0.1.0/0.1.1 attempts (called 010/011 in older task logs) had stall/failure history; keep those outcomes and do not reinstall the same failed codes without new source evidence.

For each animation experiment, keep these claims separate: request syntax known, request accepted, animation ID identified, actor family supported, pose continuity observed, completion event observed, physical support verified, recovery complete, interrupted cleanup complete. Do not re-use a failed animation code without new source evidence.

## Shower entry is a distinct integration problem

Private source inspection found that the Command shower entity lacked the inspected stock DoorParameter and EventAnimationParameter; generic CloseDoor accesses a different pool from sequential event animation. Typed guards on PushGimmick or sequential event APIs do not prove they work for the shower. Trace the stock player shower controller or another specialized native route rather than guessing generic door names or animation indexes. Queueing near the fixture does not prove entry or washing.
